# 需求卡 · P3 流式问答 + 聊天前端

## 1. 背景与目标

P2 的 `POST /chat` 是一次性返回，用户要干等几秒才看到答案。P3 做两件事：

1. 后端改成 SSE 流式输出，让答案逐字出现；同时把对话存库，支持多轮追问。
2. 起一个 umi + Ant Design X 的聊天前端，既能当独立调试页，也能被博客用 iframe 嵌成右下角挂件。

## 2. 范围

**做：**

- `conversations` / `messages` 两张表
- `POST /chat/stream`：SSE 流式，事件协议 `citations` → `token` → `done` / `error`
- 多轮上下文：带 `conversation_id` 续聊，把最近 3 轮带进 prompt
- `GET /conversations`、`GET /conversations/{id}`、`DELETE /conversations/{id}`
- 前端：`/`（全页，带知识库侧栏）、`/#/widget`（iframe 挂件）
- FastAPI 把前端产物挂在 `/ui` 下，实现前后端同源

**不做（留给 P4）：**

- 真正改博客 PageIo 的代码（本期只在 `docs/嵌入博客.md` 给出可复制的组件）
- 鉴权、限流、用户归属（`messages` 已留 `external_uid` 字段）
- 会话标题自动摘要（现在取问题前 50 字）
- Markdown 渲染（答案里的列表目前按纯文本显示）

## 3. 接口设计

### POST /chat/stream

请求：

```json
{ "question": "...", "conversation_id": "可选", "top_k": 5, "client": "web" }
```

响应 `text/event-stream`，事件顺序固定：

```
event: citations
data: {"conversation_id": "...", "citations": [...]}

event: token
data: {"text": "工具"}

event: done
data: {"conversation_id": "...", "message_id": "...", "model": "deepseek-chat"}
```

出错时发 `event: error`，`data: {"detail": "..."}`。

**为什么先发 citations：** 检索比生成快得多，先把引用推给前端，用户能立刻看到"从哪几段文档里找答案"，感知上快一截。

### 会话接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/conversations` | 列表，按 `updated_at` 倒序 |
| GET | `/conversations/{id}` | 带全部消息，用于刷新页面后还原 |
| DELETE | `/conversations/{id}` | 级联删消息 |

## 4. 表设计

```
conversations
  id            uuid pk
  title         varchar(255)   问题前 50 字
  client        varchar(32)    web / pageio / electron，加索引
  external_uid  varchar(64)    预留给 P4 的博客用户
  created_at / updated_at

messages
  id               uuid pk
  conversation_id  uuid fk → conversations.id  on delete cascade，加索引
  role             varchar(16)  user | assistant
  content          text
  citations        jsonb        仅 assistant 有
  created_at
```

`citations` 用 JSONB 而不是再建一张关联表：它只用于展示，不需要按引用反查，存成快照还能避免文档被重新 ingest 后历史答案的引用对不上。

## 5. 关键实现决策

**流式响应里自己开数据库会话，不用 `Depends(get_session)`。**
依赖注入的会话在请求结束时关闭，而流式响应的生成器比请求本身活得更久，容易踩到"会话已关闭"。所以 `event_stream()` 里用 `async with session_factory()` 自己管。

**依赖检查放在开始流式之前。**
一旦返回了 200 和 `text/event-stream` 头，就没法再改成 503 了。所以 embedding / LLM / 数据库未配置的检查在进入生成器前做完，进去以后的错误只能通过 `error` 事件送出。

**前端产物由 FastAPI 同源伺服。**
iframe 里的页面和 API 同源 → 不跨域、不用配 CORS、不涉及第三方 Cookie。博客父页面只通过 `postMessage` 控制开关。

**用 hash 路由。**
产物挂在 `/ui` 子路径下，hash 路由不需要后端配 history fallback。

## 6. 验收标准

- [x] `POST /chat/stream` 返回 `text/event-stream`，逐个 token 推送
- [x] 事件顺序为 citations → token… → done
- [x] 带 `conversation_id` 追问能理解上文（第二轮只说"这个"，模型正确理解为"工具在主进程执行"）
- [x] `conversation_id` 不存在时走 `error` 事件，不是 500
- [x] `GET /conversations/{id}` 能还原 4 条消息，assistant 消息各带 5 条引用
- [x] `GET /conversations/{不存在}` 返回 404
- [x] 知识库为空时不调用 LLM（沿用 P2 的 `retrieve` 短路）
- [x] 前端全页可用：流式逐字、引用可展开、看得到知识库文档列表
- [x] widget 页在 380×560 的 iframe 里布局正常
- [x] iframe 场景端到端通过：父页面按钮打开 → 提问 → 流式回答 → 点关闭经 postMessage 收起
- [x] 浏览器控制台无报错、无 antd 弃用警告

## 7. 踩坑记录

**antd 6 才行。** `@ant-design/x@2.9` 的 peer 要求 `antd@^6.1.1`，装 antd 5 会报 unmet peer。博客 PageIo 用的是 antd 5——这恰好说明 iframe 隔离是对的，两边版本互不干扰。

**`base` 不能在 dev 下设。** `.umirc.ts` 里写死 `base: '/ui/'`，dev 访问 `/` 会白屏，控制台提示 `<Router basename="/ui"> is not able to match the URL "/"`。改成只在 `NODE_ENV === 'production'` 时设 `publicPath`。

**umi dev 默认端口也是 8000**，和 FastAPI 撞。用 `PORT=8001 pnpm dev`。

**挂载静态目录发生在应用启动时。** 先起后端再 `pnpm build`，`/ui/` 会一直 404，要重启（或 `--reload` 下 touch 一下）后端才挂上。

**antd 6 的弃用项：** `List` 改用别的方案，`Space` 的 `direction` 改叫 `orientation`。
