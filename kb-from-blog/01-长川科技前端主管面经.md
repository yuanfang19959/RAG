## 1. 介绍下项目（以 Electron 为主）

### 30 秒版

我做了个本机开发助手 **LocalDev Agent**（Electron + React + TypeScript）。用户选一个本地仓库，用自然语言问「这项目干什么」「搜 IPC 相关代码」。链路是：用户输入 → 模型决策（Tool Calling）→ **主进程执行只读工具** → IPC 回写 React 界面。覆盖会话 Memory 和工具调用时间线。

### 2 分钟版（面试官要听「为什么」）

- **工具为什么在主进程**
渲染进程是 Chromium，不能直接 `fs`；模型参数不可信，路径必须在主进程做沙箱校验，禁止 `..` 跳出工作区。
- **安全边界**
Preload + `contextBridge` 只暴露白名单 API（chat / 选目录 / 设置），页面拿不到完整 `ipcRenderer`，更拿不到 `require('fs')`。`contextIsolation: true`，`nodeIntegration: false`。
- **Agent 防死循环**
多轮 Tool Calling 设 `MAX_TOOL_ROUNDS`，避免反复 `list_directory`。
- **和 SeekDB / Figma MCP 的区分**（一句话带过）
SeekDB 是 **开发时** 用 Figma MCP 辅助写页面；这边是 **产品里** 让 Agent 调本机工具。两套场景别混着讲。
- **局限主动说**
目前工具只读；流式还可以再做成 IPC chunk；检索是关键词不是向量。有边界比吹「完整 RAG」更像干过。

**仓库：** https://github.com/yuanfang19959/local-agent (https://github.com/yuanfang19959/local-agent)

## 3. 主进程下发 1、2、3，怎么保证渲染进程不会收到 3、2、1？

### 核心结论

**单通道、同进程对、顺序发送时，Electron/Chromium 的 IPC 本身是按序投递的**——一般不会「发 1 2 3、收 3 2 1」。
真乱序往往出在：**异步乱序完成后再回包**、**多通道并行**、**业务层自己开了并发队列**。

### 面试官想听的解法（保证业务时序）

**方案 A：一条消息带序列（推荐说）**

**方案 B：请求-响应串行（invoke）**

不要「发完三条不管」；用 `invoke/handle`，上一条 resolve 再发下一条。适合必须严格一步一步的流程。

**方案 C：主进程串行队列**

多个异步任务完成后要通知 UI 时，**完成顺序 ≠ 发送顺序**。在主进程用队列：任务完成先入队，按业务序号再 `send`，而不是 `Promise` 谁先完谁先推。

**方案 D：合并成一次**

如果三条其实是同一事务，直接 `send('batch', [1,2,3])`，从根上消灭乱序。

### 开口模板

IPC 同 channel 顺序投递一般没问题；我更担心的是异步回调乱序回写。做法是：要么主进程串行化后再 send，要么消息带 seq，渲染端按序消费；关键路径用 invoke 串行。

## 5. Hook 能在条件中调用吗？为什么？

### 结论

**不能。** Hook 必须放在函数组件（或自定义 Hook）顶层，不能放在 `if` / `for` / 嵌套函数里。

### 为什么（面试版）

React 靠 **调用顺序** 把多次 Hook 调用和内部状态链表对应起来。
条件调用会导致某次渲染少调 / 多调，顺序错位 → 状态串台、难查的 bug。

同理：自定义 Hook 内部也要遵守，保证整条调用链顺序稳定。

## 6. useState 是一个闭包吗？

### 准确说法

`useState`** 返回的 state 值，在当次渲染的函数作用域里形成闭包。**
每次渲染，函数组件重新执行，拿到的是 **那一次渲染的快照**；事件回调如果捕获了旧渲染的 state，就是「闭包旧值」问题。

### 怎么破

- 更新用函数式：`setCount(c => c + 1)`，不依赖闭包里的旧 count
- 需要「可变且同步可读」的最新值 → `useRef`
- 或者把依赖写进 `useEffect` / `useCallback` 的 deps，让回调随 state 更新

### 一句话

Hook 本身是 React 调度的状态单元；我们说的「useState 闭包」通常指 **渲染快照被事件函数捕获**，不是说 useState API 等于 JS 闭包对象。

## 7. useRef 有什么作用？

- **拿 DOM / 组件实例**：`ref={elRef}`，`elRef.current.focus()`
- **跨渲染保留可变盒子**：改 `ref.current` **不触发重渲染**（和 state 互补）
- **存「最新值」躲闭包**：`countRef.current = count`，定时器里读 ref
- **记上一轮值 / 标记**：是否首次 mount、上次 props 等

## 8. useCallback 怎么用，一般什么时候用？

### 怎么用

返回 **引用稳定的函数**（deps 不变则同一引用）。

### 什么时候用（别滥用）

该用

不该用

回调传给 `React.memo` 子组件，避免无意义重渲染

随便包一层「感觉性能好」

作为 `useEffect` 依赖，避免 effect 每 render 重跑

deps 仍每渲都变，白包

自定义 Hook 对外暴露稳定 API

无子优化、无 effect 依赖时

### 和 useMemo

- `useCallback(fn, deps)` ≈ `useMemo(() => fn, deps)`
- 贵的是 **子树渲染 / 效应重跑**，不是「多创建了一个函数」本身。

### 开口

我默认先写普通函数；只有确认子组件 memo 或 effect 依赖需要稳定引用时才加 useCallback，并保证 deps 正确。

## 9. 构造函数，有用过吗？

### JS / 业务向

- **class 组件**：`constructor(props) { super(props); this.state = ... }`——老项目见过；新代码几乎不写 class。
- **普通 class**：工具类、Error 子类、少数 OO 封装会用。
- **React 函数组件时代**：初始化逻辑放 `useState(() => init())` 惰性初始，或模块顶层，而不是 constructor。

### 结合 Electron

主进程里 `new BrowserWindow(...)`、`new Tray(...)` 就是构造；业务上更常讲「生命周期 / 单例窗口」而不是 OO 继承树。

### 一句话

用过，主要在 class 组件时期和少量工具类；现在 React 侧用 Hooks，构造函数不是日常写法。

## 10. JS 和 TS 有什么区别？继承呢？

### 区别（面试抓三点）

JavaScript

TypeScript

类型

动态，运行时才暴露问题

静态类型 + 编译期检查

产物

直接跑

编译/擦除类型后仍是 JS

工程

灵活

接口契约、重构、IDE 提示更强

TS 本质是 **JS + 类型系统**（还有 enum、namespace 等，但核心是类型）。生产里 SeekDB / Agent 都用 TS。

### 继承

**JS：**

- 原型链：`Child.prototype = Object.create(Parent.prototype)`
- ES6 `class Child extends Parent`（语法糖，底层仍是原型）
- 还有组合、混入，前端更常 **组合优于继承**

**TS 在继承上多了什么：**

- `extends` 类继承（同 JS，加类型）
- `implements` 实现接口（编译期约束，运行时没有 interface）
- 接口/类型的 `extends` 做类型扩展
- `abstract class` 抽象类（编译期约束）

### 开口模板

JS/TS 运行时行为一致，TS 多编译期类型。继承两边都能 `extends`；TS 额外用 interface / implements 做契约。业务组件我更倾向组合和 Hook 复用，而不是深继承。

## 11. `for` 和 `forEach` 有什么区别？

### 结论先说

都是遍历；差别在 **控制流、性能细节、能否中断、异步怎么写**。需要 `break` / `continue` / 精确下标控制用 `for`；只做「对每个元素副作用」用 `forEach` 更短。

### 对比表

维度

`for` / `for...of`

`Array.prototype.forEach`

中断

可 `break` / `continue` / `return` 出函数

**不能** `break`；`return` 只跳过本次回调

异步

`for...of` + `await` 可串行等

`forEach(async ...)` **不会等**，易踩坑

复杂度 / 性能

都是 **O(n)**，复杂度不更高；常数项通常更小，实测常略快

同为 **O(n)**；多一层回调调用，大数组才看得出差距

稀疏数组

`for` 按下标可能扫到空洞

`forEach` **跳过空槽**

可读性

逻辑复杂、要提前退出时更清晰

简单映射副作用时更干净

### 和 `map` / `for...in` 别混

- **要新数组** → `map`，别用 `forEach` 里 `push`
- `for...in` 遍历的是可枚举键（含原型链），不适合遍历数组元素

### 开口模板

简单遍历两者都行；要中断、要 `await` 串行、要精细下标，我用 `for` / `for...of`。`forEach` 里 `return` 不是 `break`，异步更不要用 `forEach`。

# 管理类（接手项目 / 带团队 / 质量）

## 1. 如果进来接手一个项目，你怎么快速了解项目情况？

### 原则

**先跑通，再读透；先业务链路，再代码细节；先风险清单，再改架构。**

**Day 1–2：能跑 + 能讲清业务**

**Day 5：风险与计划**

- 建议的前 2–4 周目标（先止血还是先交付）

### 人怎么问

- **产品**：最近两版需求优先级、历史坑
- **后端**：接口契约、兼容策略、联调方式
- **测试 / 运营**：高频客诉、回滚过没有
- **代码**：挑一条最热链路打日志跟一遍，比盲目通读有效

### 开口模板

我不会一上来就重构。先把环境跑通、主链路画清楚，再摸清发版和监控；第一周输出风险清单和近期目标，跟 Leader 对齐后再动刀。OceanBase 接手多站点时也是先 SEO/性能/发布链路摸清，再排治理项。

## 2. 管理团队怎么保证进度？

### 结论

进度靠 **范围清晰 + 拆到可验收 + 节奏可见 + 风险早暴露**，不是靠盯人坐多久。

### 具体做法

- **需求入口可控**
评审时砍清：Must / Should / Could；口头需求进看板才算数。
- **拆任务到「可演示」**
避免「做登录模块 5 天」这种黑盒；拆成接口联调、页面、权限、异常态，每项有完成定义（DoD）。
- **固定节奏**

- 日：站会只说「昨天完成 / 今天计划 / 阻塞」——阻塞当场认领
- 周：对照里程碑看红黄绿，调整范围而不是默默延期

- **缓冲与并行**
关键路径标出来；能并行的联调提前 mock；依赖后端的接口先定契约。
- **可视化**
看板（或简单表格）让所有人看见谁卡在哪；Owner 盯阻塞不盯敲键盘。
- **质量不和进度对立**
提测清单、冒烟用例、必要的 E2E；返工往往比「先赶后修」更吃进度。

### 结合经历

带 4 人小组做水务项目时，我把排期和联调窗口先和后端对齐；社区 Owner 时多角色协作，用里程碑（活动上线、SEO 治理、CMS 发布）管进度，范围变化就重新谈优先级，而不是加人加时长硬扛。

## 3. 如果一名组员进度不行也不加班，怎么办？

### 立场（先亮）

**不加班不是问题；持续交付不达标才是问题。** 先分清：是能力、范围、阻塞，还是意愿。

### 处理顺序

**① 事实对齐（1:1，不对众指责）**

- 任务拆得是否过大、依赖是否卡住
- 预估是否本来就不准（共担责任）
- 是否不会做、不敢问

**② 给方法，不给情绪**

- 一起把任务拆到 0.5–1 天可验收
- 每日对齐阻塞；你先 pair / code review 帮过坎
- 必要时调整任务类型（先做他能打胜仗的模块）

**③ 设观察窗口**

例如两周：明确交付物与质量底线。达标就收口；仍不行进入绩效/调岗沟通（按公司流程）。

**④ 对团队公平**

- 不默认「别人加班补他的坑」长期化
- 范围不够就砍需求或加人，而不是道德绑架加班

### 开口模板

我会先确认是估时问题、阻塞还是能力缺口。能教就短期加码辅导和拆任务；该砍范围就砍。加班不能当管理制度。若辅导后仍达不到岗位要求，按事实和 HR/上级流程处理，同时保证项目用调配兜住交付。

## 4. 怎么判断组员编码好坏？只看 bug 多少吗？

### 结论

**Bug 数量是信号，不是唯一分数。** 还要看复杂度、协作成本、可维护性和线上真实影响。

### 多维判断

维度

好的信号

差的信号

正确性

主路径稳，边界有处理

反复同模块回归

可读性

命名清晰、结构简单

魔法数、超长函数、难 CR

可维护

改一处不影响无关模块

改 UI 炸接口、无测试保护

工程习惯

自测清单、小 PR、补关键用例

巨 PR、提测靠别人兜底

协作

CR 反馈能吸收，接口先对齐

甩锅、文档/注释与实现脱节

线上影响

故障少、能快速定位

P0 多、改完不观察

### Bug 怎么「正确看」

- **分严重级别**：1 个 P0 > 20 个文案问题
- **分归属**：需求不清、设计缺陷、联调环境 ≠ 个人编码差
- **看趋势**：新人前期 bug 多但收敛快 = 可培养；老人同模块反复炸 = 态度或能力问题
- **看逃逸率**：提测前自测能挡多少；线上逃逸才是重点

### 实操手段（Owner / 组长常用）

- **Code Review**：不只找茬，看设计是否简单、有无安全/性能坑（XSS、大列表、无 key 等）
- **提测质量**：打回率、用例通过率
- **线上**：Sentry / 客诉 / 回滚记录按人/模块归因（谨慎，避免甩锅文化）
- **复杂度对冲**：让强的人碰难模块时，用设计评审降低「看起来 bug 多其实活难」的误判
