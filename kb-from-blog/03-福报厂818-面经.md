# 手写题：用户卡片（串行请求 + 竞态）

实现一个 React 卡片组件 `Demo`，根据 props `userId` 拉用户和团队信息并展示。

## 接口

两个 REST 接口，**团队接口依赖用户接口返回的 **`teamId`，必须串行。

`fetch` 即可，不用封装请求库。

## UI

一张横排卡片（样式见 `demo.less`）：

- 左侧头像图
- 右侧上：用户名、年龄、团队名
- 右侧下：成员数（`members.length`）

约束：

- `userId` 为空：不请求
- 用户还没回来：整卡显示「加载中...」
- 用户已到、团队未到：人的信息先出来，团队名显示「团队加载中...」，成员数显示 `-`
- 请求失败：显示「加载失败」（取消请求不要当成失败）

## 必须处理的点

- **串行**：先 user，再用 `user.teamId` 打 team，不要两个一起发。
- **竞态**：`userId` 从 A 快速切到 B 时，A 的响应不得写到 B 的卡片上。用 `AbortController`：`userId` 变化时 abort 上一次的 user + team 请求；`AbortError` 直接忽略。
- **切人要清态**：新的 `userId` 进来时先把 user / team / error 置空，不要闪一下上一个人的数据。
- **数据分开存**：`user`、`team` 两个 state，不要揉成一个对象（两份数据到的时间不同，合成后切人容易把旧 team 贴到新 user 上）。

# 怎么处理 props 的竞态问题

竞态：`userId` 从 A 很快切到 B，A 的请求后回来，把 B 的卡改成 A 的数据。更隐蔽的是 **A 的 user + A 的 team 后到，写进已经是 B 的卡**。demo 就是这个场景，因为 team 请求更晚。

**demo 里已经做了三件：**

- `AbortController`：`userId` 变了，cleanup 里 `abort()`，A 的 user/team 请求都停；`AbortError` 直接 return，不 `setError`。
- **先清空**：effect 一进来 `setUser(null); setTeam(null)`，界面立刻回「加载中」，不会短暂显示上一张卡。
- **依赖只有 **`userId`：换人就重跑整段串行请求，不拿过期的 `teamId` 去打 team。

**为什么 abort 特别重要：** 两个请求是串行的。只判断「回来的 userId === 当前 userId」但忘了 abort，A 的 team 仍可能在 B 的 user 已经渲染后才 `setTeam`，团队名就会错。一个 controller 绑两次 fetch，切人两个一起断。

**没有 AbortController 的备选：** 闭包里 `let cancelled = false`，cleanup 置 true，setState 前判断；或自增 `reqId`，只认最新 id。无限滚动分页同理：只认最新 page。

**不要这么写：** `setCard(prev => ({ ...prev, team }))`。prev 可能已经是下一个人，旧 team 会合并进去——这就是「合成一个变量」在竞态里更危险的原因。

## 口述 45 秒

多卡片我分层做。

**数据：** 接口分页，首屏只拿一屏。卡片上的封面图 `loading="lazy"`，进视口再下。

**无限滚动：** 列表底放一个哨兵 DOM，`IntersectionObserver` 看见了就请求下一页，数据 append。请求带 page，旧页返回就丢（竞态）。`key` 用业务 id，不要 index。

**虚拟滚动：** 数据已经很多、DOM 太多才上。容器固定高度，`scrollTop` 算出可见区间，只渲染这几行，上面用 padding 撑开。社区大赛滚榜就是虚拟列表 + `userId` 当 key，避免整表 replace 闪烁。

卡片墙还有一特：一排 n 个，虚拟化按**行**做，不是按单张卡。高度不齐（摘要有长有短）时虚拟滚动很难估总高，这种列表我优先分页 + 无限滚动，不上虚拟列表。

## 无限滚动要点

- 用 **IntersectionObserver**，别用 `scroll` 里狂读 `scrollTop`（易回流）
- `rootMargin: '200px'` 提前加载，少白屏
- 分页请求竞态：只认最新 page / AbortController（接上一题 props 竞态）
- 不要每张卡再打用户信息、团队信息；列表接口一次带齐，详情再懒拉

## 虚拟滚动原理（多列卡片）

坑：

- 卡片高度不固定 → 要测量缓存，别一上来承诺虚拟列表
- `key` 必须稳定（blogId / userId），index 会错位、图片串
- 和无限滚动可以叠：下面加载更多，上面仍只画可视行
- 库：`react-window` / `react-virtualized`；手写能讲清原理即可

## 可能追问

- **几十张卡也要虚拟滚动吗？** 不要。分页 + 图懒加载够了，虚拟列表有滚动跳动、焦点、测高成本。
- **无限滚动 vs 虚拟滚动？** 前者管「数据从哪来」，后者管「DOM 画多少」。数据 20 条无限滚就行；数据 2000 条且要一次拿着筛选，才虚拟化。
- **滚榜怎么防闪？** 稳定 key、增量 patch、节流 setState；高峰只更 Top N。
- **Observer 为啥比 scroll 好？** 浏览器算交叉，回调次数少，不在滚动热路径里读布局。

# 介绍下你们的性能优化，哪个提升最大

只讲社区官网。口径：核心模板（首页、博客列表）治理期 **RUM P75 首屏 4s→1.2s**，FCP **2.1s→0.9s**。别说全站、别说 LCP<1.2s。

**业务里怎么分：**

- **登录鉴权**：走 Cookie，前端不碰；401 拦截跳登录。
- **纯前端偏好**：语言、UI 状态 → localStorage / sessionStorage（SeekDB locale：URL > localStorage > 默认英文）。
- **埋点用户标识（ob-tm）**：Cookie + localStorage **双写** `cookieofx` + 30 分钟滑动 `sessionId`。只清 Cookie 时从 localStorage 补回来，避免同一人被运营算两个人。

# cookie 呢

我们平常一般不直接操作 cookie，因为整站登录态是 HttpOnly。

**展开（面试官追问「那 cookie 你们还用吗」）：**

- **登录 Cookie 前端不碰**

- 服务端 `Set-Cookie` + `HttpOnly` + `Secure` + `SameSite`
- JS 读不到 `document.cookie`，XSS 也偷不走登录态
- 请求浏览器自动带上，前端只处理 401 / 过期跳转
- 这就是「整站 HttpOnly、不直接操作 cookie」的意思——指的是**鉴权 Cookie**

- **但埋点 Cookie 必须前端写**

- ob-tm 的 `cookieofx` 要给 JS 读、给各子站共享，**不能 HttpOnly**
- 写到父域 `.oceanbase.com`，path `/`，社区官网 / SeekDB 共用一份用户 ID
- 同时写一份到 localStorage：用户只清 Cookie 时还能修回来
- sessionId 是 30 分钟滑动：每次上报前续期，离开 30 分钟再来算新会话

- **和 localStorage 的分工一句话**

- Cookie：要**随请求走**、要**跨子域**、要给服务端看见 → 用 Cookie
- localStorage：只给前端自己用的偏好 / 备份 → 用 Storage
- Token 不放 localStorage 当登录态（XSS 能读），登录态交给 HttpOnly Cookie

**可能再追问，短答：**

- HttpOnly：禁止 JS 读，防 XSS 偷 Cookie
- Secure：只走 HTTPS
- SameSite=Lax/Strict：减轻 CSRF；跨站 POST 要 None + Secure
- 跨子域：`Domain=.oceanbase.com`；localStorage 做不到
- 为什么不把 cookieofx 也设 HttpOnly：埋点 SDK 要读、要和 localStorage 互修，设了就双写失败
